# Tactical sector radar and QTE threat directions

Initially implemented on 2026-11-07. On 2026-11-15 the user approved the semi-transparent, architecture-free sector-radar concept for implementation. The current presentation supersedes the original square terrain map; the native-matched projectile detector and centered incoming-fire cues remain in use.

## Player-facing behavior

- A semi-transparent circular radar stays at the top-left. Its 256-logical-unit child canvas is positioned at (28, 28); the analytic disk has a small transparent outer margin. A white central dot and a faint forward cone follow the camera-relative presentation. Pitch and roll are discarded; front stays at the top of the radar.
- The disk uses 20% base opacity with a muted gray-blue tint. There are no building footprints, terrain lines, interior projectile diamonds, compass ticks, tactical title or threat-count footer. Initialization no longer discovers StaticMesh components, and regular updates no longer refresh terrain bounds. The retained legacy terrain/projection functions are not on the active rendering path.
- During native projectile QTE or FullStop, every qualifying production enemy bullet participates in a 16-sector camera-relative direction mask. Front=0, right=4, rear=8, left=12. Each occupied bearing lights a 43.2-degree coral-red arc on the inside of the disk rim. The arc and disk share one antialiased silhouette. Translucent red light fades toward the center and across the ends of the arc. Bearings 45 degrees apart retain a narrow gap, while overlapping arcs merge at the same brightness. Several bullets in one direction share a sector. There is no projectile-count cap or per-projectile radar widget; four RGBA parameters carry the occupied sectors to one material.
- Coral rings with translucent dark-red centers mark living enemies inside the disk, including enemies behind cover. The local HUD discovers loaded `BP_Enemy_Base` subclasses four times per real second, then checks validity, planar distance and the shared `IsDead` function at each 25 ms refresh. Movement and camera yaw update the positions between discoveries. The shared `Brush_RadarEnemyContact` draws each marker without allocating a widget per enemy.
- The map label `Ø 40 m` gives the diameter. The 2000 cm half-range limits enemy positions. An eligible projectile beyond that range still contributes its bearing to the outer warning ring.
- The same bullets retain the existing camera-relative filled directional darts and tapered inner crescents around the crosshair. Faceted shading, hot rims, restrained glow and dark contrast edges retain readability over the scene. This includes left, right and rear threats. The architecture-free radar has no UP/DN map annotations.
- Visual eligibility follows the existing QTE's relative-motion prediction window, separate capsule XY/Z tolerances, projectile radius and `Projectile`-profile occlusion trace. The projectile's move-ignore list and itself are ignored as in the native detector. A projectile already consumed by the QTE remains visible while it is still approaching; consumption only prevents repeat triggering.
- Normal state hides the threat overlay. Destroyed, receding, missing or occluded bullets disappear on the next visual refresh. FullStop does not stall HUD refreshes because scheduling uses real time.

Runtime logic uses Blueprints and a standard Unreal UI material. The temporary authoring helper, Python, Blueprint Assist and LabAuthoring are not runtime dependencies. No new input, map, render target, scene capture, damage or energy asset is required. Existing QTE/weapon Blueprints are not modified.

Widget defaults now use `MapRange`=2000 cm, `MapSize`=256 logical units, `ThreatRefreshSeconds`=0.025 real seconds and the unchanged centered-cue `RingRadius`=105. `TerrainRefreshSeconds` is retained for compatibility and is no longer on the active update path. The range label is calculated rather than hard-coded. Each centered cue canvas remains `4.2 × RingRadius` square. Local geometry and canvas anchors retain DPI/aspect handling.

`SourceAssets/UI/Minimap/sector-radar.hlsl` is the readable material-authoring reference. The material embeds the shader and has no runtime file include. `SectorsA` through `SectorsD` carry all sixteen direction flags, including each vector's alpha channel. `BackdropOpacity` defaults to 0.20, `ThreatOpacity` to 0.95 and `ViewHalfAngle` to 32 degrees. The view cone is an illustrative HUD shape, not a measured camera-frustum overlay.

**Show Map Panel** in `WBP_TacticalMinimap` defaults to true. Direct play in Map_Test shows the disk, range label, enemy positions and sector warnings. For live changes, call `SetMapPanelVisible(Visible)` on the local player's `TacticalMinimap.MinimapWidget`. The switch applies immediately and the centered incoming-projectile arrows remain available.

After a successful **New Game**, `BP_MainMenuController.CommitNewGame` opens the first world with the travel option `HideMinimap`. The widget applies this option during construction, before its first paint. The chapter opens Map_TrainingRoom with `ChapterTraining` and returns to Map_LabV39 with `ChapterReturn`. Both destinations use the panel default. Each world reads its own travel options, so starting a new game hides the opening radar again.

The outer warning ring uses the production enemy-projectile QTE and FullStop detection. Nearby melee and ranged enemies appear on the inner position layer even when idle.

## Incoming-threat art pass — 2026-11-07

The user's Apex screenshot is the visual reference for a broad inward dart plus a separate curved direction indicator. [EA's official description](https://www.ea.com/able/resources/apex-legends/pc/features) distinguishes 2D and 3D incoming-damage arrows; [Activision's HUD reference](https://support.activision.com/servlet/servlet.FileDownload?file=00PU0000004ZRV7MAO&retURL=%2Fapex%2Fmanuals) describes a red directional damage marker. This implementation adapts that visual language to predicted incoming projectiles. It does not claim to reproduce either game's internal renderer, or turn a prediction into an actual-damage signal. Existing damage-vignette ownership is preserved.

`RegisterThreatVisual` allocates an actor-keyed child widget / dynamic material only when no reusable slot exists. `UpdateThreatVisuals` runs after the existing Tick collection: 100 ms ease-in, real-time pulse, bounded travel-time urgency, and a 160 ms exit fade followed by collapse and actor-reference release. Peak-concurrency slots are retained for reuse, including their MIDs. Invalid / destroyed actors retain their last bearing during fade. FullStop keeps the red danger body with a narrow cold rim; real-time parameters keep animation responsive. Child widgets inherit the minimap's travel / EndPlay cleanup. No new gameplay state, input, trace or terrain collection is introduced.

Material inputs are `Direction` (camera-yaw-relative screen XY), `Urgency` (0–1), `RealTime`, `Age`, `Presence` and `Frozen`. The material itself contains the complete shader; [the readable HLSL source](../../SourceAssets/UI/Threats/incoming-threat-cue.hlsl) is an authoring reference, not a runtime include. Glow is composited in the UI material and does not depend on scene bloom. The default `Presence=0` keeps uninitialized cues hidden.

The original terrain, map anchoring, native-matched eligibility and collection graphs are unchanged. Both affected Widget Blueprints compile with zero errors / warnings.
